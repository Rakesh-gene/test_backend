# GAP-007: Process ownership and optional strict isolation

Implemented 8 November 2026. The user authorized optional containers for strict
isolation. Native commands and container commands have different explicit boundaries;
worktrees alone are never advertised as a security sandbox.

| Execution | Enforced boundary |
| --- | --- |
| Windows native | Trusted bootstrap enters a non-inheritable Job Object before dispatch. Kill-on-close covers detached/double-fork descendants and hard owner death. Filesystem permissions remain those of the OS user. |
| Linux/macOS native | Owned process groups and cancellation; escaped descendants and arbitrary filesystem access remain outside this mode's guarantees. |
| Optional strict container | Local Linux engine, pinned image ID, isolated task tree mounted at `/workspace`, read-only image filesystem, private PID namespace/init, no network/socket/host credentials, non-root command and protected root-owned lifecycle guard. |
| Native Codex assignment | Confirmed per-assignment native permission profile, including denial of Kode's private control directory. Live Windows proof is in GAP-006; other provider/OS qualification remains later work. |

Use a locally installed Linux image containing `/bin/sh`, `/usr/bin/setpriv` and the
repository's tools:

```text
kode execution container mcr.microsoft.com/dotnet/sdk:10.0
kode execution inspect
kode tree create <root>
kode command run <root> build --tree <id>
kode execution native
```

Inspect `kode command --help` for command syntax. Configuration is host-controlled
in private `.kode/control/execution.json`, outside `kode.yaml`; a repository cannot
request extra mounts, privileged execution, a Docker socket or broader networking.
The image is resolved locally to its immutable ID. Kode pins the local daemon
endpoint for dispatch and recovery, independently of later
Docker context changes. Kode never pulls automatically
and never falls back to native execution after strict-mode failure. Remote engines,
Windows images and images declaring anonymous volumes are refused. Docker or image
failure blocks execution with an actionable error.

Only an isolated writable task tree can be mounted. The original source and its
installation are preserved. Target environment variables are passed after dropping
privileges; repository `PATH`, `LD_PRELOAD` and shell startup settings cannot modify
the trusted host Docker client or root guard. Inherited host credentials are excluded.
The command has no capability to signal the root guard/init. Docker defaults for
seccomp remain enabled; no privileged/host-PID/host-network option is exposed.

Container creation intent and ownership are durable before creation/start. Cleanup
checks exact container ID (or the pre-recorded UUID name), immutable image and both
ownership labels. Recovery removes only matching owned containers and never reruns
the command. The attached stdin lifecycle watcher terminates the PID namespace when
the runner/client dies, independently of restart reconciliation. Timeout and normal
exit also remove descendants. Failed/unconfirmed cleanup retains its descriptor and
blocks recovery rather than guessing at PIDs or deleting an unrelated container.

The effective mode appears in runner status, the terminal overview and durable job
records. Native `doctor` also states its OS-user boundary. Policy changes are refused
while commands are active.

Evidence:

- `tests/process-ownership.test.ts` and `.artifacts/GAP-007-ownership.json`: real
  Windows detached double-fork child, direct-parent exit, hard owner kill and an
  unrelated process that remains alive.
- `tests/isolation.test.ts`: unavailable/remote engine refuses dispatch with no
  native marker, invalid policy is rejected, isolated tree is required, and native
  dependency receipts cannot be adopted in container mode.
- `node scripts/qualify-containment.mjs`: real Docker engine and installed SDK image;
  non-root scope and guard protection, host-secret/socket exclusion, out-of-scope
  denial, direct exit, timeout and hard runner kill. It verifies container disappearance
  **before** runner recovery and an absent escaped-write marker. Result:
  `.artifacts/GAP-007-container.json`. CI also runs this on its Linux Docker host.

Limits are deliberately retained: strict mode currently runs individual declared
commands with networking disabled. Host service/port orchestration and native
environment-receipt APIs are refused in this mode. Run declared setup/build/test
commands in the same container task tree; per-tree npm/NuGet cache paths persist in
`.kode-cache`, but container-aware receipt validation and shared cross-tree caches
need their own adapter. Native Windows installations are not copied into Linux
containers. Native environment reuse remains covered by GAP-008. macOS Docker Desktop
and other architectures require native qualification before advertising parity.

Reference semantics: [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[Docker run](https://docs.docker.com/reference/cli/docker/container/run/), and
[Docker's stdin-on-disconnect configuration](https://github.com/docker/cli/blob/master/cli/command/container/opts.go).
